# Content Bot v0.4.3 Release Notes

**Release date:** 2026-09-15

The media question can now produce its video with Google NotebookLM, so a
NotebookLM subscription replaces per-clip billing for narrated overviews.

## NotebookLM video provider

- The media question gains a fifth choice, **NotebookLM video**, whenever a
  worker is configured through `CONTENT_NOTEBOOKLM_URL`. The button is absent
  (and the ask text stays unchanged) while the worker is missing or
  `CONTENT_NOTEBOOKLM_ENABLED=false`.
- Choosing it opens a profile picker with three shipped profiles: **Technical
  for developers** (`technical_fa`), **Educational for everyone**
  (`educational_fa`), and **Short news overview** (`news_fa`). The keyboard
  and the profile names come from one table, so they cannot drift.
- The job sends the draft title and body as a `text` source and the original
  link as an `auto` source (classified as a website or a YouTube link by the
  worker), then follows the job and edits the ask message once per stage:
  `⏳ Preparing the sources...`, `📚 Creating the notebook...`,
  `📤 Uploading the sources...`, `🎬 Generating the video...`, and
  `⬇️ Downloading the output...`.
- A finished job arrives as the usual media preview: the bot downloads the
  mp4 from the worker, stores it under `data/content-bot/media/`, and offers
  the standard **Approve** / **Reject** buttons. A failed job reports the
  worker error and offers a retry that reuses the stored profile.
- `post /status` prints the NotebookLM worker URL, and the media driver stored
  on a draft is `notebooklm`, so Media Studio jobs keep working unchanged next
  to it.
- New keys: `CONTENT_NOTEBOOKLM_URL`, `CONTENT_NOTEBOOKLM_TOKEN`,
  `CONTENT_NOTEBOOKLM_ENABLED` (default `true`), `CONTENT_NOTEBOOKLM_TIMEOUT`
  (default 1800 seconds), and `CONTENT_NOTEBOOKLM_DEFAULT_PROFILE` (default
  `technical_fa`). No existing key changes meaning.
- `NotebookLM` in `content_bot/notebooklm.py` is a thin HTTP client
  (`submit`, `job`, `upload`, `download`, `session`, `pick_artifact`) with
  injectable transport functions, so the worker can be replaced or stubbed in
  tests.

## Aparat upload transport

The upload path completes the work of 0.4.2 (the previous tag stops before
these fixes):

- `request_multipart` and `request_multipart_many` return the `(status, body)`
  pair their callers unpack again. They leaked the internal
  `(status, body, headers)` triple, so every Aparat chunk and every Telegram
  file send (photo, video, document) failed with `too many values to unpack`.
- The upload server is read from the nested `data.attributes` object of
  `upload_config`, with the flat `data.server` key still accepted as a
  fallback. The flat key does not exist on the live service, so every upload
  stopped before the first chunk.
- The metadata call carries `upload_base_url`, `uploadId`, and `video` again;
  Aparat answers HTTP 400 (`upload_base_url: ...`) without them.

## Tests

`test_bot.py` covers the button visibility, the profile picker, job start
with the draft sources, one progress edit per stage, the ready preview, the
failure path, the retry with the stored profile, and the missing worker. The
shared media harness was extracted so the handler-level suites no longer
re-run the base tests. Content Bot suite: 414 tests.

## Upgrade

```bash
cd /path/to/content-manager
git pull --ff-only
sed -i 's/^CONTENT_BOT_IMAGE_TAG=.*/CONTENT_BOT_IMAGE_TAG=0.4.3/' .env
docker compose pull content-bot
docker compose up -d content-bot
```

The NotebookLM worker is optional and stays off until
`./manage.sh notebooklm-enable` runs; without it the bot behaves exactly as
before.
