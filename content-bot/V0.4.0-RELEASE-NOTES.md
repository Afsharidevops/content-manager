# Content Bot v0.4.0 Release Notes

**Release date:** 2026-09-14

Multi-channel publishing: one approved draft can now reach several
destinations, each one in its own voice, with an independent result.

## LinkedIn

- `content_bot/linkedin.py` implements the LinkedIn REST publisher:
  `POST /rest/posts` for text, and
  `POST /rest/images?action=initializeUpload` plus a binary `PUT` for an
  image, with the created post URN read from the `x-restli-id` header. Every
  call carries `LinkedIn-Version` and `X-Restli-Protocol-Version`, retries
  `429`/`5xx` with exponential backoff (2s, 4s, 8s), and ends in one readable
  `LinkedInError` when the provider keeps refusing.
- `content_bot/channels.py` adds `LinkedInChannel`: one channel per configured
  account, so a personal profile (`urn:li:person:<id>`) and a company page
  (`urn:li:organization:<id>`) can publish side by side. Video and document
  posts are refused with a clear message instead of failing silently.
- `build_commentary()` turns a draft into post text (title on the first line,
  source link once at the end) and trims it to the 3000-character limit
  without cutting a word in half.
- `content_bot/http.py` gained `request_response()`, which keeps the response
  headers that the post URN lives in; `request_bytes()` is unchanged.

## Social accounts

- `content_bot/accounts.py` reads `social-accounts.yaml` from the policy
  directory (the deployed copy lives under `data/content-manager/config/` and
  is git-ignored), with `CONTENT_LINKEDIN_*` as the single-account fallback
  and `CONTENT_LINKEDIN_ACCOUNTS` accepting the whole mapping as JSON or YAML.
  Tokens are never hardcoded, and an account without a token is skipped with a
  log line instead of failing the start.
- Targets use the key `platform_account` (`linkedin_personal`,
  `linkedin_company`, `bale`, `eitaa`, ...) in drafts, buttons, and
  publication rows. Telegram and Instagram keep their own approve-time paths
  and are not written as targets.
- `docs/LINKEDIN-SETUP.md` covers the app, the OAuth flow, the author id, the
  account file, token rotation, and troubleshooting.

## Per-destination adaptation

- `content_bot/adapt.py` rewrites the draft body for each destination before
  publishing. Tone profiles ship for `linkedin_personal` (first person,
  technical, opinionated, founder voice), `linkedin_company` (educational,
  neutral, brand voice), and `telegram` (concise, news); a LinkedIn account
  follows the tone of its type.
- Profiles and limits are overridable in the `tones:` section of
  `editorial-policy.yaml`, and the rewrite prompt itself can be replaced by
  `<tone>.md` in `prompt-templates/` inside the policy directory
  (`CONTENT_PROMPT_DIR`).
- Adaptation only touches the body: the title, source link, and media captions
  keep the existing helpers, and any failure - or
  `CONTENT_ADAPT_ENABLED=false`, or no writer - falls back to the untouched
  draft text.
- The result is cached as a content variant in `data/content-bot/state.json`,
  so retrying a failed publish never calls the writer twice for the same text.

## Multi-target publishing and the publication ledger

- A draft may carry `targets:` (strings or `{platform, account}` mappings);
  otherwise `publishing.targets` in the policy applies; otherwise the
  **All targets** button publishes to every configured automatic channel.
- Every attempt is one publication row: `id`, `content_id`, `platform`,
  `account`, `status` (`published`/`failed`/`skipped`), `remote_id`,
  `published_at`, and a capped `error`. One destination failing never stops
  the others, and **All targets** reports one summary line per target.
- The existing flows are unchanged: Approve/Reject, the manual platform
  package, Instagram publishing, and drafts without targets behave exactly as
  before. A deployment with no new keys and no accounts publishes the same
  text to the same channels as 0.3.0.

## Configuration

New environment keys (all optional):

| Key | Default | Meaning |
| --- | --- | --- |
| `CONTENT_LINKEDIN_ACCESS_TOKEN` | - | Fallback account token |
| `CONTENT_LINKEDIN_ACCOUNT` | `personal` | Fallback account key |
| `CONTENT_LINKEDIN_ACCOUNT_TYPE` | `person` | `person` or `organization` |
| `CONTENT_LINKEDIN_PERSON_ID` / `CONTENT_LINKEDIN_ORGANIZATION_ID` | - | Ids that build the author URN |
| `CONTENT_LINKEDIN_AUTHOR_URN` | - | Explicit URN, wins over the ids |
| `CONTENT_LINKEDIN_LABEL` | - | Chooser label override |
| `CONTENT_LINKEDIN_API_BASE` | `https://api.linkedin.com` | REST host |
| `CONTENT_LINKEDIN_API_VERSION` | `202601` | Pinned `LinkedIn-Version` |
| `CONTENT_LINKEDIN_TIMEOUT` | `60` | Per-request timeout (seconds) |
| `CONTENT_LINKEDIN_RETRIES` | `3` | Attempts per request |
| `CONTENT_SOCIAL_ACCOUNTS_FILE` | `social-accounts.yaml` | Account file inside the policy directory |
| `CONTENT_ADAPT_ENABLED` | `true` | Turn the per-destination rewrite off |
| `CONTENT_PROMPT_DIR` | `<policy>/prompt-templates` | Prompt template directory |

## Tests

New suites: `test_linkedin.py`, `test_social_accounts.py`, `test_adapt.py`,
`test_publications.py`, and `test_multichannel.py`; the operator panel gained

## Upgrade

```bash
cd /path/to/content-manager
git pull --ff-only
sed -i 's/^CONTENT_BOT_IMAGE_TAG=.*/CONTENT_BOT_IMAGE_TAG=0.4.0/' .env
docker compose pull content-bot
docker compose up -d content-bot
./manage.sh content-channels
```

State files are additive: `publications` and `content_variants` are new keys
in the existing `data/content-bot/state.json`, and no migration step exists or
is needed.
