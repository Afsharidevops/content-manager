# Backup and Restore

`./manage.sh backup` archives the stack configuration and runtime data as a
checksum-protected tarball, and `./manage.sh restore` puts an archive back.
Backups are as complete as the files the stack actually uses: `.env`, the
`data/` tree (SQLite databases, service state, media, secrets), and
`docker-compose.yml`. Image references and container image IDs are recorded in
the same archive so an image set can be identified later.

Archives live outside the repository by default
(`../<repo>-backups`, override with `--destination` or
`CONTENT_MANAGER_BACKUP_DIR`) and are written with mode `600`.

## What the stack stores

There is no external database requirement for the single-host Compose stack.
Every service keeps its state as files under `data/`:

| Service | State | Location |
| --- | --- | --- |
| Smart Router | SQLite databases, observations, learned model | `data/smart-router/` |
| 9router / OmniRoute | Gateway configuration and accounts | `data/9router/`, `data/omniroute/` |
| Hermes Agent | configuration, sessions, logs, `.env` | `data/hermes/` |
| Content Bot | drafts, media, Instagram token, panel queue | `data/content-bot/` |
| Media Studio | generated media and job records | `data/media-studio/` |
| Operator panel | console token and edit backups | `data/panel/` |
| n8n / Open WebUI / Caddy | workflows, chats, certificates | `data/n8n/`, `data/open-webui/`, `data/caddy/` |
| Stack secrets | keys generated by the installer | `data/stack-secrets/` |

PostgreSQL is only required for the multi-replica (Kubernetes) deployment,
where the Smart Router chart ships PostgreSQL and Redis for shared sticky
routing and HA state. The Compose stack in this repository never needs it.
If a future deployment moves data into PostgreSQL, back it up with
`pg_dump` in addition to this archive tooling.

## Section names

`./manage.sh backup-sections` prints the supported section names:

| Section | Paths | Use it for |
| --- | --- | --- |
| `env` | `.env` | Copying configuration and secrets between servers |
| `secrets` | `data/stack-secrets/` | Rotating/keeping generated keys |
| `hermes` | `data/hermes/` | Agent configuration, sessions, logs |
| `router` | `data/smart-router/`, `data/9router/`, `data/omniroute/` | Routing policy, observations, gateway accounts |
| `content` | `data/content-manager/`, `data/content-bot/` | Drafts, media, Instagram state, panel queue |
| `media` | `data/media-studio/` | Generated media and job records |
| `panel` | `data/panel/` | Console token and edit backups |
| `n8n` | `data/n8n/` | Workflows and credentials |
| `openwebui` | `data/open-webui/` | Chats and users |
| `s3` | `data/rustfs/` | Bundled RustFS objects and logs (see `docs/S3-STORAGE.md`) |
| `caddy` | `data/caddy/` | Certificates and Caddy state |
| `execution` | `data/execution-workspace/` | Agent execution workspace |
| `state` | `data/stack-state/` | Update history and release state |
| `compose` | `docker-compose.yml`, `stack.lock.json` | Deployment definition and image digests |

A backup without `--only` contains every section and is marked `full` in its
manifest. `backup --only env,panel` contains only those paths and is marked
partial.

## Creating backups

```bash
# Full backup (containers are paused briefly for a consistent filesystem copy)
./manage.sh backup

# Named full backup in a specific directory
./manage.sh backup --destination /srv/backups --label before-upgrade

# Section backups
./manage.sh backup --only env,secrets --destination /srv/backups
./manage.sh backup --only content,panel --label nightly

# Encrypted at rest with age
./manage.sh backup --age-recipient age1example...

# List archives with the sections they contain
./manage.sh backup-list
./manage.sh backup-list --json
```

Every archive has a `.sha256` sidecar (verified before a restore) and a
`.meta.json` sidecar that records the sections, checkout root, stack version,
and creation time, so `backup-list` and `restore` do not have to unpack the
archive to learn what it holds.

`./manage.sh update` creates a pre-update backup automatically. Images are
rolled back automatically when readiness fails; data is never rolled back
silently.

## Restoring

```bash
# Full restore: replaces .env and data/ after a pre-restore safety backup
./manage.sh restore /srv/backups/hermes-stack-20260911T070000Z-before-upgrade.tar.gz

# Restore one section without touching the rest of the stack
./manage.sh restore /srv/backups/hermes-stack-...-content_panel.tar.gz

# Restore files but do not start services
./manage.sh restore ARCHIVE --no-start

# Skip automatic host-path rewriting (see "Moving to another server")
./manage.sh restore ARCHIVE --no-relocate
```

A restore:

1. verifies the `.sha256` sidecar when present,
2. rejects archives with unsafe paths,
3. creates a full pre-restore safety backup,
4. stops the services,
5. replaces a full archive's `.env` and `data/` — or, for a partial archive,
   moves only the archived paths aside and copies them back,
6. rewrites absolute host paths in the restored `.env` when the archive came
   from a different checkout root,
7. validates `docker compose config`, starts the services, waits for health,
   and puts the previous state back if anything fails.

Full restores replace the whole `data/` tree. Partial restores merge: files
that are not part of the archive stay exactly as they are, which is why a
section backup can be restored on a server that already runs the rest of the
stack.

## Moving the stack to another server

1. On the old server: `./manage.sh backup` (or at least
   `--only env,secrets,content,panel,...` for the sections you need).
2. Copy the archive and its `.sha256`/`.meta.json` sidecars to the new server.
3. On the new server: clone the repository and run `./install.sh` once, so
   image profiles, the Docker network, and ownership exist. The installer's
   choices are overwritten by the restore.
4. `./manage.sh restore /path/to/archive.tar.gz`.

During the restore, values that end in `_HOST_PATH` or `_STACK_PATH` are
rewritten from the old root to the new one (for example
`EXECUTION_WORKSPACE_HOST_PATH` and `PANEL_STACK_PATH`). Other host-specific
settings are restored as-is and may need a manual look:

| Setting | Why it may need an edit |
| --- | --- |
| `*_BIND_IP` | Host addresses differ per server |
| `INSTAGRAM_MEDIA_PUBLIC_BASE_URL`, `data/content-bot/media-base-url.txt` | The public media hostname belongs to the new deployment |
| Reverse-proxy targets | Point the router proxy at the new host |
| `*_PUBLIC_BASE_URL` | Public URLs served by the new host |

Verify after a restore:

```bash
./manage.sh health
./manage.sh status
./manage.sh content-status     # when the content stack is installed
./manage.sh panel-status
./manage.sh instagram-media-status
```

## Automation

```bash
# Nightly full backup at 03:30, keep the destination outside the repository
30 3 * * * cd /home/user/lab/projects/content-manager && \
  ./manage.sh backup --label nightly --destination /srv/backups >>/var/log/content-manager-backup.log 2>&1
```

Add `--age-recipient` to keep archives encrypted at rest, and copy archives to
another machine: a backup that only exists on the host it protects is not a
backup.

## Troubleshooting

- `backup could not read all stack data` — run the command as root or with
  sudo available; service files are owned by container UIDs.
- `backup checksum verification failed` — the archive or its `.sha256` sidecar
  is damaged; use another archive.
- `partial backup does not record the sections it contains` — the archive was
  created before section metadata existed or was modified; restore it as a
  full archive or extract it manually.
- `restored services did not become ready` — the previous state was put back
  automatically. Inspect `./manage.sh logs` and retry with `--no-start` to
  inspect files before starting services.
